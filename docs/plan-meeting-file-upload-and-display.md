# Plan: Meeting File Upload and Display

**PRD**: @docs/prd-meeting-file-upload-and-display.md
**Дата**: 2026-08-17

## Технические решения, зафиксированные при планировании

- **Хранилище файлов**: локальный диск на этой итерации (директория задаётся env `STORAGE_DIR`, по умолчанию `apps/server/uploads/`, добавляется в `.gitignore`). Доступ к файлам изолируется за интерфейсом `FilesStorageService`, чтобы позже заменить на облачное хранилище (S3 и т.п.) без изменения контроллеров/сервисов.
- **`creatorId` на `Meeting`**: поле обязательное (`String`, not null), без backfill фиктивным владельцем — существующие тестовые встречи без владельца очищаются перед миграцией, т.к. это pre-prod окружение без реальных пользовательских данных.
- **Множественная загрузка**: `Meeting` 1—N `MeetingFile`, без версионирования (соответствует "не в скоупе" из PRD).
- **Статус файла**: поле `status` на `MeetingFile` вводится сейчас с единственным значением (`UPLOADED`), зарезервировано под будущую обработку (транскрибация), которая явно не в скоупе этой фичи.
- **Прогресс загрузки**: реализуется через `XMLHttpRequest` на клиенте (у `fetch` нет upload-прогресса), а не через персистентный "pending" статус на сервере — запись `MeetingFile` создаётся только после успешного сохранения файла.

## Фазы реализации

### Фаза 1: База данных — владелец встречи и модель файлов

**Цель**: Дать модели `Meeting` владельца и завести модель для метаданных прикреплённых файлов — основа для прав доступа и последующего API.
**Затрагивает**: database, backend
**Задачи**

- [] Добавить поле `creatorId` (String, FK → `User`) в модель `Meeting` в `apps/server/prisma/schema.prisma`
- [] Добавить модель `MeetingFile` (`id`, `meetingId` FK, `fileName`, `mimeType`, `sizeBytes`, `storagePath`, `status`, `uploadedById` FK → `User`, `createdAt`) и связь `Meeting.files MeetingFile[]`
- [] Очистить/пересоздать локальные dev-данные без владельца и прогнать `pnpm prisma migrate dev --name add-meeting-owner-and-files` в `apps/server`
- [] Обновить `CreateMeetingDto`/`MeetingsService.create`, чтобы `creatorId` брался из `request.user.sub` (JwtAuthGuard), а не приходил от клиента

### Фаза 2: Backend — хранение файлов и правила валидации

**Цель**: Реализовать серверный сервис сохранения файлов на диск и конфигурируемые (не захардкоженные в нескольких местах) правила допустимых форматов и максимального размера.
**Затрагивает**: backend
**Задачи**

- [] Завести конфигурируемые константы `ALLOWED_MIME_TYPES`/`ALLOWED_EXTENSIONS` (mp3, wav, m4a, mp4) и `MAX_FILE_SIZE_BYTES`, читаемые из env с дефолтами (одно место определения, переиспользуемое контроллером и DTO)
- [] Реализовать `FilesStorageService`, абстрагирующий физическое сохранение (диск, путь из `STORAGE_DIR`), с интерфейсом, допускающим замену бэкенда хранения в будущем
- [] Подключить Multer через `@nestjs/platform-express` (`FileInterceptor`), выставить лимит размера на уровне Multer как первый барьер — до того как файл будет полностью считан в память/на диск
- [] Реализовать проверку mime-type + расширения и размера с понятными сообщениями об ошибке (400 Bad Request)

### Фаза 3: Backend — API загрузки файлов и авторизация

**Цель**: Дать эндпоинт загрузки файла к встрече (только для создателя) и вернуть список файлов вместе с данными встречи.
**Затрагивает**: backend
**Задачи**

- [] Добавить `POST /meetings/:id/files` (multipart/form-data, под `JwtAuthGuard`) в `MeetingsController` (или выделенный `MeetingFilesController`)
- [] В сервисе: 404 если встреча не найдена, 403 если `request.user.sub !== meeting.creatorId`, иначе сохранить файл через `FilesStorageService` и создать запись `MeetingFile`
- [] Расширить `MeetingsService.findOne`, чтобы включать связанные `files` (Prisma `include`) и `creatorId` в ответе — нужно фронтенду для списка файлов и для определения прав на загрузку
- [] Добавить response DTO для файла (`id`, `fileName`, `sizeBytes`, `mimeType`, `status`, `createdAt`, `uploadedById`), не раскрывающий `storagePath` наружу

### Фаза 4: Frontend — страница деталей встречи (read-only)

**Цель**: Создать `/meetings/[id]` с отображением основной информации о встрече и списком прикреплённых файлов.
**Затрагивает**: frontend
**Задачи**

- [] Добавить `getMeeting(accessToken, id)` в `apps/client/src/lib/api/meetings.ts`, расширить тип `Meeting` полями `creatorId` и `files: MeetingFile[]`
- [] Создать `apps/client/src/app/meetings/[id]/page.tsx` (client component, обёрнутый `useRequireSession`, по аналогии с `/meetings/new`)
- [] Отобразить `title`/`date`/`participants` встречи и список файлов (имя, размер в человекочитаемом виде, дата загрузки, статус), включая пустое состояние "файлов пока нет"
- [] Сохранять `userId` (`sub` из JWT) в сессии рядом с email (`apps/client/src/lib/auth/session.ts`), чтобы вычислять `isCreator = session.userId === meeting.creatorId` (нужно и в Фазе 5)
- [] Обработать состояние "встреча не найдена" (404)

### Фаза 5: Frontend — блок загрузки файла

**Цель**: Дать создателю встречи загрузку файла записи с клиентской валидацией, индикатором прогресса и защитой от повторной отправки.
**Затрагивает**: frontend
**Задачи**

- [] Добавить `uploadMeetingFile(accessToken, meetingId, file, onProgress)` в `apps/client/src/lib/api/meetings.ts` через `XMLHttpRequest` (для получения прогресса загрузки)
- [] Показывать блок загрузки только когда `isCreator === true`
- [] Клиентская валидация формата/размера перед отправкой теми же константами, что и на сервере
- [] Индикатор прогресса (progress bar/процент) и блокировка повторной отправки того же файла до завершения текущей загрузки
- [] После успешной загрузки добавлять файл в список без перезагрузки страницы
- [] Обработать и показать ошибки: недопустимый формат, превышение размера, сетевая ошибка, 403 (не создатель), 404 (встреча не найдена) — по аналогии с `formError` в `/meetings/new`
- [] Прогнать изменения формы/progress-индикатора через skill `ui-ux-pro-max` (согласно правилу в `apps/client/CLAUDE.md`) и поправить то, что она укажет

### Фаза 6: Тесты, устойчивость и документация

**Цель**: Покрыть новый функционал тестами и обновить проектную документацию, чтобы она не разошлась с кодом.
**Затрагивает**: backend, frontend, docs
**Задачи**

- [] Backend e2e-тесты: успешная загрузка; недопустимый формат отклонён; превышение размера отклонено; 401 без токена; 403 для не-создателя; несколько файлов на одну встречу; `GET /meetings/:id` возвращает `files` и `creatorId`
- [] Проверить поведение списка файлов, когда файлов ещё нет
- [] Ручная проверка в браузере (`pnpm dev`): успешная загрузка, ошибка формата, ошибка размера, повторный клик во время загрузки, вид страницы для не-создателя
- [] Обновить `apps/server/CLAUDE.md` (модель `MeetingFile`, новый эндпоинт, `FilesStorageService`, env `STORAGE_DIR`) и `apps/client/CLAUDE.md` (страница `/meetings/[id]`, upload API, изменения в `session.ts`)
- [] При необходимости обновить корневой `CLAUDE.md`, если новая инфраструктурная зависимость (например, `STORAGE_DIR`) значима для всего workspace
