# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm start:dev    # nest start --watch
pnpm build        # nest build
pnpm start:prod   # node dist/main (run build first)
pnpm lint         # eslint --fix over src/apps/libs/test
pnpm test         # jest (unit tests, *.spec.ts colocated under src/)
pnpm test:e2e     # jest --config ./test/jest-e2e.json
pnpm test:cov     # jest with coverage
```

Run a single test file or test name:

```bash
pnpm test -- src/files/file-filter.spec.ts
pnpm test:e2e -- test/auth.e2e-spec.ts
pnpm test:e2e -- -t "rejects an incorrect password with 401 Unauthorized"
```

## Architecture

- Standard NestJS module structure: `src/app.module.ts` wires `PrismaModule`, `AuthModule`, `UsersModule`, `FilesModule`, and `MeetingsModule` (no root `AppController`/`AppService` — the boilerplate `GET /` "Hello World" route was removed since nothing in the app used it); `src/main.ts` bootstraps, applies a global `ValidationPipe({ whitelist: true, transform: true })`, and listens. New features should follow the same controller/service/module split.
- **Database**: Prisma (pinned to v6 — v7 requires Node 22.12+, this repo runs 22.11) talks to the Postgres container defined in the root `docker-compose.yml`. Schema lives at `prisma/schema.prisma`; migrations in `prisma/migrations/`. `PrismaService` (`src/prisma/prisma.service.ts`) extends `PrismaClient` and is provided by a `@Global()` `PrismaModule`, so any module can inject it without re-importing. Connection config comes from `apps/server/.env` (`DATABASE_URL`, `JWT_SECRET` — gitignored, not committed) loaded via `ConfigModule.forRoot({ isGlobal: true })` in `AppModule`.
  - After changing `schema.prisma`: `pnpm prisma migrate dev --name <name>` (regenerates the client too), or `pnpm prisma generate` alone if only the client needs regenerating.
- **Users**: `src/users/` — `UsersService` is the only place that touches Prisma's `user` model. `findByEmail(email)` reads; `create(email, password)` hashes the password with `bcrypt` internally before persisting, so callers never handle raw hashing — a caller can't accidentally store a plaintext password by going through this service. `changePassword(id, oldPassword, newPassword)` also verifies `oldPassword` with `bcrypt.compare` against the stored hash before hashing and persisting the new one — this is the one case where password _verification_ lives in `UsersService` rather than `AuthService` (see below), because it's a self-service action on an already-JWT-authenticated user, not a login credential check. `UsersModule` exports `UsersService` for other modules (currently only `AuthModule`) to import.
- **Auth**: `src/auth/` — owns authentication/authorization only, not user data. `AuthController` exposes `POST /auth/register` and `POST /auth/login` (both return `{ accessToken }`); `AuthService` calls `UsersService` for lookup/creation, verifies the password on login with `bcrypt.compare` (password _verification_ stays here for login since it's a credential check, whereas password _hashing_ on creation lives in `UsersService` — see above), and signs JWTs via `@nestjs/jwt` (`JwtModule.registerAsync` reads `JWT_SECRET` from `ConfigService`, 1h expiry). DTOs (`RegisterDto`, `LoginDto`) use `class-validator` decorators — validation only fires because of the global `ValidationPipe`, so e2e tests must configure the same pipe on their `TestingModule` (they don't get `main.ts`'s bootstrap for free). `AuthModule` imports `UsersModule` and also provides/exports `JwtModule` and `JwtAuthGuard` (`src/auth/guards/jwt-auth.guard.ts`) so other modules can protect routes without redefining JWT config — import `AuthModule` and `@UseGuards(JwtAuthGuard)` on the controller. The guard expects `Authorization: Bearer <token>` and rejects with 401 if missing/invalid; on success it sets `request.user = { sub, email }`.
- **CORS & dev port**: `main.ts` calls `app.enableCors({ origin: process.env.CLIENT_URL ?? 'http://localhost:3000' })` so the browser-based `apps/client` (fixed on :3000, see root `CLAUDE.md`) can call this API cross-origin. Since both apps default to port 3000, the local `.env` (gitignored) sets `PORT=3001` for this app in dev — `apps/client` points at it via `NEXT_PUBLIC_API_URL` (see `apps/client/CLAUDE.md`). If you change either app's dev port, update the other side's default to match.
- **Meetings**: `src/meetings/` — `MeetingsController` (guarded by `JwtAuthGuard`, so all routes require a valid access token) exposes `POST /meetings`, `GET /meetings`, `GET /meetings/:id` (404 via `NotFoundException` when the id doesn't exist, 401 via the guard when unauthenticated). `MeetingsService` talks to `PrismaService`'s `meeting` model (`title: String`, `date: DateTime`, `participants: String[]` — a native Postgres array, no join table; `creatorId: String`, FK -> `User`, set from `request.user.sub` in the controller — never accepted from the client). `CreateMeetingDto` validates `title` (non-empty string), `date` (`@IsISO8601()`), `participants` (array of strings, empty array allowed). `findOne` does `include: { files: true }` and returns a `MeetingWithFilesResponseDto` (`dto/meeting-response.dto.ts`) — `creatorId` is a plain column so `findAll`/`create` already include it without an `include`.
- **Meeting files**: `src/meetings/meeting-files.controller.ts` + `meeting-files.service.ts` — `POST /meetings/:id/files` (multipart/form-data, field `file`, `JwtAuthGuard`) via `FileInterceptor('file')` (picks up `FilesModule`'s registered Multer defaults — see below) and `@UploadedFile(MeetingFileValidationPipe)`. `MeetingFilesService.attach`: 404 if the meeting doesn't exist, 403 if `request.user.sub !== meeting.creatorId`, otherwise saves the file via `FilesStorageService` and creates a `MeetingFile` row. Every failure path (404, 403, or a failed DB write) deletes the file `FileInterceptor`'s `diskStorage` already wrote to disk before the check ran — skipping that cleanup leaks orphaned files, see `FilesStorageService.delete()`. Response is an explicit `MeetingFileResponseDto` (`dto/meeting-file-response.dto.ts`) that omits `storagePath`.
- **`src/files/`** — infrastructure shared by the meeting-files feature: `files.constants.ts` holds `getAllowedMimeTypes`/`getAllowedExtensions`/`getMaxFileSizeBytes` (mp3/wav/m4a/mp4, 500 MB default) and `resolveStorageDir`, all read through the injected `ConfigService` rather than `process.env` directly — `files.constants.ts` can be `require()`'d before `ConfigModule.forRoot()` loads `.env`, so a direct `process.env` read would silently miss overrides (confirmed via `dist/app.module.js`'s `require` order). `FilesModule` wires `MulterModule.registerAsync` (`diskStorage`, UUID filename — never `file.originalname`, which is user-controlled — `limits.fileSize` as the first barrier, `fileFilter` via `isAllowedMeetingFile`) and provides `FilesStorageService` (disk I/O: `save`/`resolvePath`/`delete`, creates `STORAGE_DIR` on boot) and `MeetingFileValidationPipe` (a `PipeTransform`, not a plain function — Nest resolves pipes passed by class reference to `@UploadedFile()` through its DI container, so it needs to be an injectable to receive `ConfigService`; wraps `ParseFilePipe` with `skipMagicNumbersValidation: true` since `diskStorage` never populates `file.buffer`, which `FileTypeValidator` needs for magic-number sniffing). `STORAGE_DIR` env var, defaults to `apps/server/uploads/` (gitignored). A file exceeding `MAX_FILE_SIZE_BYTES` gets Nest's built-in `PayloadTooLargeException` (413), not 400 — that's `@nestjs/platform-express`'s standard mapping for multer's `LIMIT_FILE_SIZE`, not something this app special-cases.
- Jest config for unit tests lives inline in `package.json` (`rootDir: "src"`, matches `*.spec.ts`, colocated next to the code they cover, e.g. `src/files/file-filter.spec.ts`). E2E tests live under `test/` with their own config (`test/jest-e2e.json`) and boot a full Nest application (`test/auth.e2e-spec.ts`, `test/meetings.e2e-spec.ts`, `test/meeting-files.e2e-spec.ts`) rather than testing a controller in isolation. These hit the real Postgres container (no mocking) and use unique/generated data per test instead of resetting DB state between runs. `meeting-files.e2e-spec.ts` points `STORAGE_DIR` at a fresh `os.tmpdir()` directory for the file so uploads don't land in the real `apps/server/uploads/`, and temporarily overrides `MAX_FILE_SIZE_BYTES` for the oversized-file test — when doing that, restore env vars with `delete process.env.KEY` rather than `process.env.KEY = previousValue` when `previousValue` was `undefined`; assigning `undefined` sets the literal string `"undefined"` (env values are always strings) instead of unsetting the key, which silently breaks `Number(...)`-based config reads in later tests.
- ESLint runs `typescript-eslint`'s `recommendedTypeChecked` plus `eslint-plugin-prettier/recommended`, meaning Prettier violations surface as ESLint errors here (unlike the client app, which uses `eslint-config-prettier` instead). Prettier's actual rules come from the repo root (`../../.prettierrc.json`) — there is no per-app `.prettierrc`.
- Jest's `expect.any(...)` matchers are typed `any`, which trips `@typescript-eslint/no-unsafe-assignment` when used inside an object literal passed to `toEqual`. Prefer separate assertions (e.g. `expect(Object.keys(body)).toEqual([...])` + `expect(typeof body.x).toBe('string')`) over `toEqual({ x: expect.any(String) })`.
