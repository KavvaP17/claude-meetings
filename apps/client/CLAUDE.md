```bash
pnpm dev          # next dev
pnpm build        # next build
pnpm start        # next start (serves the production build)
pnpm lint         # eslint
pnpm test         # vitest run

```

## Architecture

- Next.js 16, App Router, TypeScript, Tailwind CSS v4 (via `@tailwindcss/postcss`). Path alias `@/*` resolves to `./src/*`.
- Tests are colocated next to the code they cover (`src/app/page.test.tsx`) and run under Vitest with jsdom (`vitest.config.ts`, `vitest.setup.ts` loads `@testing-library/jest-dom` matchers).
- **Known issue**: rendering _any_ hook-using component (confirmed down to a bare `useState`) under the current Vitest 2.1.9 + React 19.2.8 + jsdom setup throws `Cannot read properties of null (reading 'useState')` from React's `resolveDispatcher()` — a pre-existing environment bug, not something a specific component does wrong (the same components render fine in the actual browser via `pnpm dev`). Clearing the Vite/Vitest cache and `resolve.dedupe: ['react', 'react-dom']` did not fix it; it likely needs a Vitest 3.x upgrade. Until fixed, hook-based components (i.e. anything under `src/app/`) can't be unit-tested here — verify them manually in the browser instead, and see the skipped test in `src/app/page.test.tsx` for how to re-enable coverage once resolved. This does **not** block testing plain functions with no React involved — `src/lib/api/file-validation.test.ts` and `src/lib/format.test.ts` are ordinary Vitest specs and run fine; prefer pulling logic out of a page into a plain `lib/` function when it's worth covering in isolation.
- ESLint is `eslint-config-next` (core-web-vitals + typescript) plus `eslint-config-prettier` to disable rules that would conflict with Prettier. Prettier itself is configured at the repo root (`../../.prettierrc.json`), not per-app.
- UI components use HeroUI v3 (`@heroui/react`, `@heroui/styles`, `tailwind-variants`). `src/app/globals.css` imports `@heroui/styles` right after `tailwindcss` — order matters. No `HeroUIProvider` is needed in v3. Use the `heroui-react` skill (`.claude/skills/heroui-react` at the repo root) when adding components — its v3 API differs substantially from v2 (compound components like `Card.Header` instead of flat props) — see the skill before assuming v2 patterns apply.
- **Backend API**: `src/lib/api/client.ts` has the shared `apiFetch<T>()` helper (base URL from `NEXT_PUBLIC_API_URL`, defaulting to `http://localhost:3001` in dev — the server runs on :3001, not :3000, so it doesn't collide with this app's dev port; see `apps/server/CLAUDE.md`), the typed `ApiError` (carries HTTP `status` + message extracted from Nest's error body), the exported `extractErrorMessage` helper (reused outside `apiFetch` by the upload path below, so both stay consistent), and `authHeaders(accessToken)` (`{ Authorization: 'Bearer ...' }` — shared by every `lib/api/*.ts` module below rather than each redefining it). `src/lib/api/auth.ts` (`registerUser`, `loginUser`), `src/lib/api/meetings.ts` (`getMeetings`, `getMeeting`, `createMeeting`, `uploadMeetingFile`), and `src/lib/api/users.ts` (`getCurrentUser`, `GET /users/me` -> `UserProfile { id, email, name, avatarUrl, createdAt }`, matching the server's `UserProfileResponseDto`) build on top of it. `getMeeting(accessToken, id)` (`GET /meetings/:id`) returns `MeetingWithFiles` (extends `Meeting` with `files: MeetingFile[]`) — kept as a separate type from `Meeting` rather than making `files` a field on `Meeting` itself, since `GET /meetings` (the list) never returns it. `uploadMeetingFile(accessToken, meetingId, file, onProgress)` is built on `XMLHttpRequest`, not `fetch`/`apiFetch` — only `xhr.upload.onprogress` gives real upload progress.
- **Session / auth guard**: `src/lib/auth/session.ts` stores `accessToken`, `email`, and `userId` in `localStorage` (`setSession`/`getSession`/`clearSession` — there's no cookie or server session, it's purely client-side). `userId` is decoded from the JWT `sub` claim inside `setSession` itself via `src/lib/auth/jwt.ts`'s `decodeAccessTokenSub` (no signature verification — the token was just issued by our own login/register call, this is purely for client-side UI, the server re-verifies on every request); `setSession`'s parameter type intentionally stays `{ email, accessToken }` so the login/register call sites didn't need to change when `userId` was added. `src/lib/auth/useRequireSession.ts` is the guard hook for pages that require a logged-in user: it reads the session via `useSyncExternalStore` (not `useEffect`+`setState` — that trips the `react-hooks/set-state-in-effect` lint rule and, for `useSyncExternalStore` specifically, needs its `getSnapshot` to return a cached/stable reference or React throws an infinite-loop warning) and redirects to `/login` when there's none. Returns `{ session, logout }`; consumers should render `null`/a `Spinner` while `session` is falsy. **Known issue**: this redirect fires on a hard page reload / direct URL navigation even with a valid session in `localStorage` (reproduces on `/` too, not specific to any one page) — normal in-app navigation (clicking a `Link`/`Button`) is unaffected. Not yet root-caused; likely a `useSyncExternalStore` hydration timing issue.
- **Registration / Login**: `src/app/register/page.tsx` and `src/app/login/page.tsx` — client components built with HeroUI's `Form`/`TextField`/`Card` composition, cross-linked to each other. Register mirrors the server's `RegisterDto` validation (email format, 8-char min password) client-side via `TextField`'s `validate` prop; login has no client-side password rule since the server just checks it against a hash. Both show server errors (register: 409 duplicate email; login: 401 invalid credentials; both: network failures) in a `role="alert"` banner, include a show/hide toggle on the password field, and on success call `setSession` and redirect to `/`.
- **Dashboard (`/`) and meeting creation (`/meetings/new`)**: both protected by `useRequireSession`. The dashboard greets the user by email, has a "Log out" button (`logout()` from the hook — no confirmation dialog; logout isn't a destructive/data-loss action), shows the total meeting count and the 3 most recent as links to `/meetings/[id]` (`GET /meetings` has no `userId` scoping or ordering server-side, so this list is global across all users, sorted client-side by `date` descending), and a "Create meeting" button. A 401 from `getMeetings` (expired token) calls `logout()`. `/meetings/new` posts to `POST /meetings` (`title`, `date` as ISO 8601 via `Date.toISOString()`, `participants` parsed from a comma-separated field) and redirects back to `/` on success.
- **Meeting detail (`/meetings/[id]`)**: protected by `useRequireSession`; reads the dynamic segment via `useParams()` (this is a Client Component page, so `params` isn't awaited here — see [Next's dynamic-routes doc](https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes) on the Client Component case). Shows title/date/participants and the files list (name, `formatFileSize` from `src/lib/format.ts`, upload date, a status `Chip` colored via a small `status -> color` map — not hardcoded, since `MeetingFileStatus` is reserved for future values beyond `UPLOADED`). 404 from `getMeeting` shows a dedicated "Meeting not found" card instead of the generic error state; a non-404/401 load error and the upload error both render through the same `role="alert"` pattern as `formError` in `/meetings/new`. The upload block (hidden `<input type="file">` triggered by a `Button`, `sr-only` + `tabIndex={-1}` + `aria-label` — not `aria-hidden`, which is invalid ARIA on a focusable element and Chromium ignores it) only renders when `session.userId === meeting.creatorId`; `isUploading` disables the trigger for the duration and drives a HeroUI `ProgressBar`. Client-side format/size validation (`src/lib/api/file-validation.ts`) mirrors the server's `ALLOWED_EXTENSIONS`/`MAX_FILE_SIZE_BYTES` defaults — duplicated intentionally, there's no shared package between `apps/client` and `apps/server` in this workspace (see root `CLAUDE.md`). On success the returned file is appended to local state directly, no refetch.

- **Profile (`/profile`)**: protected by `useRequireSession`; on mount fetches the current user via `getCurrentUser` (`GET /users/me`), following the same fetch/loading/error pattern as `/meetings/[id]` (a 401 calls `logout()`). Renders the avatar (HeroUI's `Avatar`, image src resolved against `API_URL` since the server's `avatarUrl` is a path relative to the API origin — not the client's, falling back to an `Avatar.Fallback` initial derived from the name or email when `avatarUrl` is empty), the name (falling back to the email when `name` is `null` — the email line is then omitted to avoid showing it twice), the email, and the registration date via the same `Intl.DateTimeFormat` pattern as `/meetings/[id]`, plus an "Edit profile" button (`Card.Footer`, `router.push('/profile/edit')`). Display is read-only for now; `/profile/edit` itself lands in a later phase, so the button currently routes to a 404. Checked against the `ui-ux-pro-max` skill (accessibility/touch/color/typography domains) — the page's error/loading states, `Card.Title` heading, and `text-muted`/`text-danger` tokens already match the conventions established on `/`, `/login`, `/register`, and `/meetings/[id]`; no changes were needed.

Whenever a new page needs to be usable only by a logged-in user, wrap it with `useRequireSession` rather than re-deriving the redirect logic.

## UI/UX review

Any change to this app's UI (new pages/components, edits to existing markup, styling, or interaction behavior) must be checked against the `ui-ux-pro-max` skill (`.claude/skills/ui-ux-pro-max` at the repo root) before the change is considered done. Invoke the skill and run its `scripts/search.py` against the relevant domains (`ux` for accessibility/touch/forms, `color`/`typography` for visual changes) to check the change against its rule database, and fix what it flags (or note explicitly why a flagged item doesn't apply) before wrapping up.
